# Unseen — клиент

Single-page application на Lit: light DOM и глобальные CSS-файлы, единственная зависимость рабочей сборки — `lit`. Крипто-примитивы и wire-кодек берутся из `shared/`, оттуда же приходит `@noble/hashes` для потокового SHA-256 файловых чанков.

Слои: маршрутизация и загрузка приложения, UI-компоненты, реактивное состояние (Signals), доменная логика (FSM сессии, отправка и приём, WebAuthn, Markdown, передача файлов), хранилище, транспорт, воркеры, глобальные lifecycle-хуки.

## Routing

Разбор `location` даёт один из трёх маршрутов:

- `landing` — путь `/`, монтируется `<landing-view>`.
- `chat` — путь `/r402` с fragment из 43 символов base64url (32 байта секрета), монтируется `<chat-view>`.
- `invalid` — всё остальное: молчаливый редирект `navigation.navigate('/', { history: 'replace' })`. Отдельной страницы ошибки нет — это убирает различимое состояние на стороне клиента.

Приложение слушает `hashchange`, `popstate` и первичную загрузку. Умный remount: корневой элемент не пересоздаётся, если его тег уже соответствует маршруту; для чата обновляется только секрет.

Модуль `chat-view` грузится динамически, и `customElements.define` обязан отработать до `createElement` — иначе setter секрета отсутствует. Если модуль не загрузился (например, вкладка пережила редеплой и чанка с этим хешем больше нет), каркас не остаётся в «Соединение…»: `main.chat` и sr-only статус переходят в `data-state="LOAD_FAILED"`, плейсхолдер показывает `chat.placeholder.loadFailed`.

Состояния PEER_RECONNECTING, RECONNECTING, TERMINATED и блокирующие подтверждения рисуются внутри `<chat-view>` (обратный отсчёт до следующей попытки, автопереход на лендинг через 10 с, панель с `role="alert"`) — отдельных элементов для них нет.

Штамп версии — не элемент, а фрагмент в футере лендинга и чата: ссылка `git@<7 символов SHA>` на коммит в GitHub. SHA подставляется на сборке (`UNSEEN_RELEASE_SHA` или `git rev-parse HEAD`); при пустом или неформатном значении фрагмент не рендерится.

Все компоненты — light DOM без shadow root, глобальный CSS через `@layer`. Это требует CSP `style-src 'self'` без adopted stylesheets.

## State

Реактивное состояние — тонкая обёртка `Signal` поверх `EventTarget`: геттер и сеттер `.value` с ранним выходом по `Object.is` и `.subscribe(listener)`, возвращающий функцию отписки.

| Сигнал                              | Значение                                                    |
| ----------------------------------- | ----------------------------------------------------------- |
| `sessionState`                      | текущее состояние FSM сессии                                |
| `sessionMode` / `peerMode`          | свой режим и режим peer: `RAM` или `PRF`                    |
| `myRole`                            | initiator или joiner                                        |
| `reconnectAttemptAtMs`              | момент следующей попытки reconnect, для отсчёта в UI        |
| `messages`                          | лента сообщений (chat / system / file)                      |
| `prunedCount`                       | счётчик сообщений, вытесненных по DOM-cap                   |
| `fileTransferSupported`             | доступность передачи файлов (OPFS + Worker + Web Locks)     |
| `fileTransferReady`                 | boot-sweep завершён                                         |
| `transferActive` / `incomingActive` | состояния отправляющего и принимающего FSM                  |
| `attachmentChanged`                 | сигнал изменения карты завершённых вложений `attachmentMap` |
| `sessionReceivedBytes`              | суммарный объём принятого за сессию                         |

## Точки входа сессии

При загрузке чата:

1. Разбор URL, невалидный маршрут → редирект.
2. Чтение записи `StoredSession` под непрозрачным ключом из секрета.
3. Запись есть → `sessionMode = 'PRF'`, переход в `RESUMING` (unwrap через WebAuthn PRF).
4. Записи нет → `sessionMode = 'RAM'`, переход в `CONNECTING` (первый HELLO с intent `create`).
5. Claim Web Lock против повторной вкладки в режиме `ifAvailable`; lock занят → мгновенный `terminate('duplicate_tab')`.

Любой сбой decrypt, разрыв счётчика или неверное направление в `ACTIVE` завершают сессию. Порядок финализации и коды причин — `02-protocol.md §TERMINATED`; здесь к нему добавляется сброс файлового состояния (см. «Сброс файлового состояния»).

## Lifecycle-хуки

**Выгрузка страницы.** Отслеживается `pagehide` и `beforeunload`. Обработчик закрытия WS при выгрузке не завершает сессию принудительно: синхронная очистка хранилища во время unload стёрла бы PRF-зеркало и сломала бы переживание перезагрузки. На `pageshow` флаг сбрасывается.

**BFCache.** При восстановлении из BFCache (`pageshow.persisted`) сессия принудительно завершается: состояние → `TERMINATED`, лента очищается, все непрозрачные OPFS-директории зачищаются. Сессия BFCache не переживает.

**Инвариант заголовка.** `document.title` всегда `peer@unseen ~ $ wait`, переустанавливается на `visibilitychange` и `pageshow`. Никаких контекстных суффиксов и значка на favicon: заголовок в стиле терминала менее опознаваем в переключателе задач и на скриншоте ОС.

**View Transitions.** Переходы оборачиваются в View Transitions API, кроме `FATAL_ENDING` и `TERMINATED` — анимация при завершении сессии неуместна.

## Хранение

| Где                           | Что                                                    | Когда                                                                        |
| ----------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------- |
| `sessionStorage[storageKey]`  | `StoredSession` (см. `02-protocol.md §Storage schema`) | только PRF: запись на `UPGRADING_LOCAL → ACTIVE` и `REKEYING → ACTIVE`       |
| `localStorage['c7XmK9-bN4q']` | `'en' \| 'ru'`                                         | языковая настройка                                                           |
| Непрозрачная OPFS-директория  | файловые чанки                                         | живёт только во время передачи; очистка при TERMINATED, загрузке, BFCache    |
| WebAuthn credential           | эфемерный passkey на комнату                           | живёт на authenticator пользователя; signal Unknown Credential при terminate |
| IndexedDB, cookies            | —                                                      | не используются                                                              |

`storageKey`, `lockKey` и имя OPFS-директории — непрозрачные base64url из 11 символов, выведенные через HKDF. Ни одно из них не содержит подстрок `unseen`, `session`, `room`, `lock`, `transfer`, `file`.

## WebAuthn

**Opt-in upgrade (RAM → PRF).** В `UPGRADING_LOCAL` запрашивается регистрация passkey для комнаты: платформенный authenticator, обязательная user verification, алгоритмы Ed25519 (предпочтительно) и ES256 (запасной), расширение PRF с eval на `prfSalt`, таймаут 60 с. Отображаемое имя косметическое (`Room 402 <5 случайных символов>`), не выводится из секрета или `roomId`; username и displayName совпадают, чтобы в менеджере паролей ОС не осело лишнее.

Исходы: успех → wrap session_key, запись `StoredSession`, `sessionMode = 'PRF'`, RELAY `mode_upgraded`, возврат в `ACTIVE`; отмена пользователем → `ACTIVE` без изменений; сбой (PRF не выдал результат, транспортная ошибка) → `ACTIVE` без изменений плюс системное сообщение `mode_upgrade_failed`. Апгрейд опционален, его провал не трогает сессию.

**Resume.** При найденном зеркале запрашивается аутентификация по сохранённому credential (UV обязательна, PRF на `prfSalt`, таймаут 60 с); на время запроса состояние остаётся `RESUMING`. По результату PRF выводится `wrap_key`, разворачивается session_key, дальше resume probe → `ACTIVE`. Отказ в самом запросе (`passkey_resume_get_rejected`) сессию не завершает: она переходит в `RESUME_LOCKED` — экран с кнопками повторить и завершить, отправка заблокирована, повтор возвращает в `RESUMING`. Остальные сбои (`passkey_resume_no_credential`, `passkey_resume_prf_missing`, `passkey_resume_unwrap_failed`) завершают сессию, хранилище очищается при финализации.

**Signal на terminate.** При штатном завершении менеджеру учётных данных отправляется необязательный сигнал, что per-room passkey можно удалить. Делается по возможности, сбои игнорируются, отсутствие API — no-op.

## Защита от повторной вкладки

Эксклюзивный Web Lock под непрозрачным именем (`lockKey`) запрашивается в режиме `ifAvailable`: lock занят другой вкладкой → `terminate('duplicate_tab')`. Успешный claim удерживается всю сессию и явно освобождается при завершении; браузер дополнительно снимает lock при закрытии или падении вкладки. Поверхность угроз `lockKey` та же, что у ключа `sessionStorage`.

## i18n

Язык (`en` | `ru`) — реактивный сигнал: берётся из сохранённой настройки в `localStorage`, иначе определяется из `navigator.languages` (первая метка, начинающаяся с `ru`, даёт RU) с откатом на `en`; смена языка тут же пишется обратно. Перевод по ключу с подстановкой `{placeholder}`. EN — базовый словарь, RU — overlay той же формы; структурное равенство проверяется типами, расхождение полей даёт ошибку typecheck.

Время форматируется `Intl.DateTimeFormat` и `Intl.RelativeTimeFormat`; источник времени — внедряемый интерфейс часов на базе `new Date().toISOString()`. Имена эмодзи SAS (EN и RU) — отдельная карта поверх замороженного пула, не часть frozen-артефакта.

## Markdown

Подмножество. Инлайн: bold (`**`), italic (`*`), inline code (`` ` ``), ссылка `[text](url)` и автоссылка — голый `http://` или `https://` URL превращается в ссылку, хвостовая пунктуация `.,;:!?)` отбрасывается. Блочные: заголовки `#`–`######` (рендерятся жирным) и fenced code blocks.

Лимиты: до 500 инлайн-токенов, глубина выделения до 3, парсинг не дольше 200 мс. Парсинг идёт в отдельном Web Worker: он запускается заранее при монтировании `chat-view` и сообщает о готовности, таймаут отсчитывается после готовности и ограничивает только парсинг, не загрузку воркера. Превышение токенов — предупреждение и откат к простому тексту, воркер продолжает работать; таймаут — то же плюс прерывание и перезапуск воркера, что ограничивает DoS через тяжёлый парсинг.

Ссылки: allowlist схем `http:` и `https:`, иначе откат к буквальному `[text](url)`. Отображается всегда `host` плюс путь, host остаётся в punycode.

## Санитизация Unicode

Применяется ко всем peer-сообщениям перед рендером:

- **Bidi-управляющие** U+202A–U+202E, U+2066–U+2069 и неявные метки U+200E, U+200F, U+061C удаляются.
- **NFC normalize** для консистентного рендера.
- **Combining marks** (категория Mn) ограничены 4 подряд — защита от Zalgo.
- **Zero-width** сохраняются и оборачиваются в `<span class="zw-marker" aria-label="zero-width">` для подсветки через CSS: удаление сломало бы легитимные сценарии, поэтому символы помечаются, а не вырезаются.

Отдельный строгий вариант для имён файлов: NFC, удаление bidi и невидимых, замена управляющих символов и разделителей пути (`/ \ : |`) на `_`, обрезка до 255 UTF-8 байт, префикс `_` у ведущей точки; пустое имя, `.` и `..` отвергаются.

## Лента сообщений

Скользящее окно ограничено 500 сообщениями в DOM; входящие батчатся через `requestAnimationFrame`, при переполнении старые вытесняются и UI показывает индикатор с числом вытесненных. При прокрутке вверх лента не дёргается, появляется значок перехода к последнему сообщению. Системный плейсхолдер ожидания снимается при подключении peer.

## SAS и burn

`<sas-badge>` — non-modal, рендерится рядом с composer в ACTIVE: 5 эмодзи и локализованные имена в подписи, `aria-live="polite"` с задержкой 150 мс (чтобы избежать двойного объявления при быстрых сменах состояния). Подтверждения в UI нет: пользователи сверяют по второму каналу параллельно с активной сессией, не сошлось — burn.

`<burn-button>` — two-step: первый клик переводит в armed на 3 с, второй в этом окне даёт `terminate('user_panic')` без буфера `FATAL_ENDING`. Безусловный escape hatch: срабатывает, даже если сессия не инициализирована или уже завершена, а UI не отреагировал. Синхронно очищается `sessionStorage`, затем `location.replace('/')`; редирект ждёт очистки OPFS, но не дольше 500 мс.

## Передача файлов

### Composer attach

Кнопка-скрепка появляется, когда `sessionState === 'ACTIVE'` и передача поддерживается; до ACTIVE скрыта, textarea при этом доступна для черновика. Активна только при полном условии:

```
fileTransferSupported && fileTransferReady && sessionState === 'ACTIVE' && transferActive === null && incomingActive === null
```

Иначе рендерится неактивной (идёт инициализация OPFS или уже есть передача). Слот один глобальный: одновременно одна передача в любом направлении.

Выбранный файл проходит очистку имени; превью-чип показывает очищенное имя, не сырое `file.name`. При отправке получателю уходит `file_offer`.

### Фазы file-bubble

| Фаза              | Render                                                    | Кто видит                                        |
| ----------------- | --------------------------------------------------------- | ------------------------------------------------ |
| `offer`           | системная строка «имя · размер [принять] [отклонить]»     | получатель                                       |
| `awaiting-accept` | системная строка «имя · размер [отмена]»                  | отправитель                                      |
| `inflight`        | системная строка «→ имя · {percent}%» с отменой           | обе стороны, у отправителя стрелка «←»           |
| `verifying`       | системная строка «✓✓ имя»                                 | отправитель, пока ждёт подтверждения целостности |
| `attachment`      | user-message, имя файла — встроенная ссылка на скачивание | обе стороны после полного успеха                 |
| `unavailable`     | системная строка «имя · передача отменена или вытеснена»  | при отмене или вытеснении                        |

Фазы до вложения — inline-flex системные строки с иконочными кнопками. В фазе вложения клик по имени запускает скачивание: из OPFS-хендла у получателя, из ссылки на `File` в памяти у отправителя. Сохранение идёт через `showSaveFilePicker`, при его отсутствии или сбое — через `<a download>` с blob URL, который отзывается по возврату фокуса или по backstop-таймеру.

### Воркеры и FSM

**Проба возможностей и boot-sweep** запускаются один раз при загрузке чата. Проба идёт первой и без lock: отдельный воркер проверяет OPFS root, `createSyncAccessHandle`, Web Locks и `ReadableStream`; провал или таймаут 3000 мс дают `fileTransferSupported = false`. Затем вкладка захватывает shared Web Lock, имя которого совпадает с непрозрачным именем её OPFS-директории, — liveness-маркер живой сессии: захват строго до создания директории, браузер отпускает lock при уничтожении документа. Под exclusive lock `OPFS_LOCK_NAME` идёт boot-sweep: удаляются все директории с непрозрачными именами, кроме текущей сессии и тех, чьи имена числятся held или pending в `navigator.locks.query()`. Итог sweep даёт `fileTransferReady`.

**Отправляющий воркер** читает `File` потоково, режет на чанки и шифрует каждый (счётчик резервируется блоками по 64), отправляет с управлением потоком по кредитам (soft cap 192 KiB, hard cap 256 KiB). По завершении считает потоковый SHA-256 и шлёт `file_complete`.

**Принимающий воркер** пишет в OPFS через `SyncAccessHandle`. Каждый чанк расшифровывается и проходит проверку границ (монотонный `seq`, длина ≤ `CHUNK_DATA_MAX_BYTES`, суммарный объём ≤ заявленного), пишется в файл и обновляет потоковый SHA-256; прогресс шлётся не чаще раза в секунду и не чаще чем раз на мегабайт. На `file_complete` сверяется тройной инвариант (размер, число чанков, хеш); при совпадении уходит `file_complete_ack`, вложение регистрируется с источником OPFS.

| Таймаут                    | Значение | Сторона                                                             |
| -------------------------- | -------- | ------------------------------------------------------------------- |
| `OFFERED_TIMEOUT_MS`       | 60 000   | отправитель отменяет offer, если accept не пришёл                   |
| `OFFER_PENDING_TIMEOUT_MS` | 60 000   | получатель отвергает offer, если пользователь не нажал accept       |
| `RECV_STALL_TIMEOUT_MS`    | 30 000   | получатель — быстрый отказ, если accept отправлен, но чанки не идут |
| `VERIFYING_TIMEOUT_MS`     | 30 000   | отправитель — отказ, если подтверждение целостности не пришло       |

На любой таймаут, отмену или фатальную ошибку идёт двусторонняя отмена: RELAY `file_cancel` с `tid`, `side` и `reason`.

### Download-only

Приложение не декодирует и не рендерит вложения inline: нет `createImageBitmap()` и никакого декодирования недоверенных байтов, поэтому риск native-decoder на контролируемых атакующим данных внутри приложения отсутствует. Любой тип, включая `image/svg+xml`, отдаётся только на скачивание; декодирование возможно лишь когда пользователь сам открывает скачанный файл — вне области защиты.

### Сброс файлового состояния

При завершении сессии активные передачи отменяются, blob-URL отзываются, OPFS-директория сессии удаляется под exclusive lock. Panic-редирект ждёт завершения очистки не дольше 500 мс; страховкой служат sweep всех непрозрачных директорий при открытии лендинга, boot-sweep следующего чата и BFCache restore. Каждый sweep пропускает директории с живым liveness-lock, поэтому директория активной сессии в другой вкладке не удаляется, а orphan-директории такого lock не имеют и удаляются. Очистка собственной директории liveness-lock не учитывает: после panic-редиректа документ уничтожен и lock отпущен.

## Доступность

- Контраст и семантика по WCAG 2.2 AA; axe-core прогоняется как E2E-гейт с тегами wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa и best-practice.
- Область нажатия: 44×44 для кнопок composer, не меньше 24×24 для иконочных кнопок в строках передачи файла (WCAG 2.5.8). Имя файла во вложении — встроенная ссылка, для неё исключение по 2.5.5 и 2.5.8.
- `aria-live="polite"` для SAS-бейджа, индикаторов статуса и системных событий.
- `prefers-reduced-motion` пропускает View Transitions, CSS-медиазапрос отменяет `:active`-трансформации.
- Блокирующие подтверждения — inline-панель с `role="alert"`; деструктивное действие — двухшаговый `<burn-button>`.
- Клавиатура: Enter и Shift+Enter в textarea, фокусные кольца через `:focus-visible`.

## Сборка

На этапе сборки из шаблонов рендерятся два HTML-файла с плейсхолдерами из английского словаря: оболочка лендинга (`/`) и предрендеренный каркас чата (`/r402`).

Рабочая сборка: SHA-384 SRI на `<script>`, `<link rel="stylesheet">` и `<link rel="modulepreload">` для синхронно достижимых чанков; разделение бандла (парсер Markdown и воркеры — отдельными чанками); имена с хешем содержимого. Сборка для разработки идёт без SRI и без разделения, с sourcemap.

Обе сборки проверяют ссылки: каждый статический и динамический импорт и каждый `new URL(...)` воркера в выпущенном JS обязан указывать на выпущенный файл, иначе сборка падает. Рабочая сборка дополнительно падает, если в бандл просочился `data-testid` или тестовый хук `__unseenTest`.
